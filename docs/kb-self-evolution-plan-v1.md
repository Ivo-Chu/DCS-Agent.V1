# DCS Agent 知识库自进化方案 v1

> 状态：**草案**（待用户评审，批准前不作为实施依据）
> 日期：2026-09-30
> 取代关系：无（首版）
> 说明：本方案在 2026-09-30 对话版设计基础上，系统性融合了市面成熟方案的优秀设计（AWS Bedrock Managed KB、Progress Agentic RAG/REMi、FastGPT、RAGFlow、Glean 系 AI KM 产品、实在智能热更新架构等），借鉴出处见 §7 对照表。

## 0. 设计原则（来自成熟方案的共识）

1. **人在回路，分级准入**：2026 年全行业无"全自动自进化"成品，成熟形态是"机器检测/起草 + 人批准"。按知识风险分级：权威源低风险自动入库，高风险（权限/财务/流程制度）必须人工一键审批。
2. **Quality in, quality out**（RAGFlow 核心理念）：解析与分块质量决定全链路上限，优先投入。
3. **权威源唯一（Canonical Source Policy）**：每个知识域指定唯一权威源，重复内容指向权威版本，冲突裁决留痕可审计。
4. **基础设施与模型解耦**（AWS Bedrock 设计）：Embedding/Rerank/LLM 均为可配置组件，更换模型不动管道代码——适配集团接口将来可能换模型的现实。
5. **引用落地（Citation-grounded）**：每条回答必须标注引用 chunk + 文档版本；无引用不回答。这也是治理"过度拒答/幻觉"的锚点。
6. **更新是业务的副产品**：知识更新尽量挂在已有动作上（文档变更、工单关闭、差评反馈），不设专职维护岗。

## 1. 知识的自动采集、清洗与更新

### 1.1 源接入：Connector + 按源数据模型（借鉴 AWS Managed KB）

每个源一个 Adapter，统一输出 `RawDocument`，并声明自己的**解析策略**（而非全局一套解析器）：

| Adapter | 源 | 解析策略要点 |
|---|---|---|
| wiki-docs | 制度/Wiki 文档目录 | 模板化分块：按"第 X 条/章节标题"保留条款结构（借鉴 RAGFlow 模板分块） |
| dcs-code | DCS C# 源码注释/接口 | 按类/方法边界切，保留命名空间路径为 sectionPath |
| oracle-meta | Oracle 元数据（只读） | 表/字段注释结构化抽取，天然小 chunk |
| wecom-notice | 企微公告 | 时间戳 + 发布人元数据，弱信任源 |
| faq-ticket | FAQ/工单沉淀 | **走 QA 对提取通道**（见 1.3） |

### 1.2 变更捕获：CDC 双模（借鉴 2026 主流热更新架构）

- **事件触发**：文档目录挂 watcher / 源系统 webhook → 变更事件进轻量队列，分钟级入库；
- **定时兜底**：node-cron 每日凌晨全量 sha256 比对，三态判定（新增/变更/失效），只对变更块重嵌——控制集团 Embedding 接口配额消耗。

### 1.3 双通道知识形态（借鉴 FastGPT）

- **chunk 通道**（默认）：语义分块，约 500 token、10% 重叠，标注 `sourceUri / sectionPath / effectiveDate / contentHash / trustLevel`；
- **QA 对通道**（FAQ/工单/高频未命中问题专用）：用 DeepSeek 把材料提炼成"问-答"结构入库，用户问题直接匹配问答对——对"设备怎么调参"这类排查型问题命中率显著优于 chunk。两通道同库共存，检索时合并 rerank。

### 1.4 解析质量兜底（借鉴 RAGFlow）

- 扫描件/复杂表格预留 DeepDoc 类深度解析器接口（独立引入，不引入整个平台）；
- 提供**分块可视化检查工具**（CLI/简单页面）：能看每个 chunk 边界，支持手动调整——坏分块不靠重跑，靠定点修。

## 2. 知识质量评估体系

### 2.1 四维检测

| 维度 | 策略 | 借鉴点 |
|---|---|---|
| 去重 | sha256 精确 + embedding 余弦 > 0.95 近似；重复块置 `duplicateOf` 指向**权威版本** | Canonical Source（Darwin 系 AI KM） |
| 纠错 | 规则校验（表名/字段/工号对 Oracle 元数据）+ DeepSeek 事实一致性抽取比对 | — |
| 过时 | **新鲜度评分**：`freshness = f(文档年龄, 编辑频率, 最近人工核验时间)`；按知识类型设半衰期（价格政策短、架构原则长）；过期自动降权并通知 Owner | 半衰期/TTL（Darwin、国内 2026 实践） |
| 冲突 | 同主题聚类 + LLM 两两判定；按"源权威优先级 + 时效"给出**裁决建议**，低置信进人工队列；**裁决全部留痕可审计** | 权威源解析 + 审计日志（Darwin） |

### 2.2 知识责任制（Ownership）

每个知识域登记 Owner（落本地元数据）：过时提醒、缺口报告、冲突待办都路由到对应 Owner——技术检测替代不了业务治理，这是成熟方案反复强调的一点。

### 2.3 质量分与准入

`qualityScore = 源信任度 × 新鲜度系数 × 历史反馈分`。高风险域（权限/财务/制度）无论分数一律走**人工一键审批队列**（Human-in-the-Loop 准入）；低风险权威源自动入库。

## 3. 基于反馈与日志的闭环优化

### 3.1 信号体系

- **显式**：企微回答卡片点赞/点踩 + 纠错入口（稀疏但权重高）；
- **隐式**（主信号，借鉴 Aura-RAG）：追问率、改写重查率、复制答案、同会话重复提问。

### 3.2 持续评估：从"发布前门禁"升级为"持续遥测"（核心借鉴 Progress REMi）

原方案只有发布前 gold set 回归，升级为双层：

1. **发布前**：gold set（从点赞样本沉淀）回归评测，不达标阻止发布——保险丝；
2. **发布后持续**：对线上流量抽样，用 DeepSeek 持续打三项指标——**groundedness（回答是否有引用支撑）、context relevance（召回是否相关）、answer accuracy**——指标回归先于用户投诉暴露问题，输出质量看板。

### 3.3 闭环三动作

- **差评归因**：召回缺失 → 调分块/查询改写/rerank 阈值；答案错 → 修 prompt/引用约束；
- **缺口发现**：低召回分问题定期 embedding 聚类，输出"高频未命中 TOP N"给知识 Owner，自动补采 + 人工补录双入口；
- **检索权重自学习**（二期，借鉴 Aura-RAG）：用隐式反馈训练轻量排序调整（如对"错误码类问题"上调 QA 对通道权重），不重训模型、不动基础设施，只调检索侧权重。

### 3.4 Agentic 更新提案（借鉴 Darwin/实在智能，"自进化"的务实形态）

后台 Agent 定期扫描：文档 diff、工单关闭记录、差评样本、缺口报告 → **自动起草知识更新提案**（新增 QA 对 / 修订 chunk / 标记过时），推送 Owner 一键批准入库。机器起草、人拍板——这是 2026 年成熟产品的共同形态，也是本方案"自进化"的落地点。

## 4. 版本管理与回滚

| 机制 | 设计 | 借鉴点 |
|---|---|---|
| 三态标记 | chunk 运行时状态：`生效 / 失效 / 待确认`；检索只召回"生效"，"待确认"（新入库未审批/冲突未裁决）默认不参与 | 实在智能热更新状态机 |
| 批次入库 | 每次入库生成 `batch_id`，逻辑删除（置 `validTo`），物理不动 | — |
| manifest + active 指针 | 发布 = 切 `active_version` 指针；**回滚 = 指针切回，秒级完成**，无需重建索引 | 版本快照（行业共识） |
| 灰度 | 新批次先对测试群/白名单 userid 生效（复用 identity 解析），观察 1-2 天 REMi 指标再全量 | — |
| 审计 | 采集/审批/发布/回滚/冲突裁决全量 changelog，落本地 SQLite（Oracle 只读不可写） | 合规行业审计实践 |
| 空间控制 | 快照最多保留 5 份，超期物理清理（C 盘余量 ≈9GB 硬约束） | — |

## 5. 系统架构与模块划分

```
src/kb/
  connectors/   # 各源 Adapter（声明式解析策略，按源数据模型）
  pipeline/     # 解析(含深度解析器接口)、清洗、模板化分块、QA对提取、hash 三态比对
  quality/      # 去重(权威源指向)、纠错、新鲜度评分、冲突检测+裁决留痕、质量分
  store/        # LanceDB 版本化(chunk+QA对双通道)、三态标记、manifest、active指针、回滚
  serving/      # 混合检索(向量+关键词) + 双通道合并rerank + 引用标注（对接现有链路）
  eval/         # gold set 回归 + REMi 式持续遥测(groundedness/relevance/accuracy) + 质量看板
  feedback/     # query_log、显式/隐式反馈采集、差评归因、缺口聚类、(二期)检索权重学习
  proposer/     # Agentic 更新提案：扫描 diff/工单/差评 → 起草更新 → Owner 审批
  ops/          # CDC 调度(事件+定时)、灰度、审计 changelog、Owner 路由
```

边界约定（与现有架构一致）：

- **企微 Channel/Adapter 层只新增"反馈卡片"与"Owner 审批通知"渲染，不进 Agent 核心**；
- 检索服务改为从 `store/` 读 active 版本 + 三态过滤，其余链路不动；
- Embedding/Rerank/LLM 全部走配置注入（原则 4），当前落集团 HTTP 接口 + DeepSeek。

## 6. 实施顺序（四阶段）

| 阶段 | 内容 | 理由 |
|---|---|---|
| P1 地基 | 版本化存储 + 三态标记 + manifest + 回滚 | 一切进化的前提，无回滚不敢自动更新 |
| P2 入库 | connectors + pipeline（含 QA 对通道）+ 质量门（人工审批全开） | 先让新知识能安全进库；自动化比例此时为零 |
| P3 闭环 | query_log + 反馈卡片 + gold set + REMi 遥测 + 缺口报告 | 先积累 2-4 周数据，让指标说话 |
| P4 进化 | Agentic 更新提案 + 检索权重自学习 + 逐步放开自动准入 | 数据足够后再放权，人机比例渐进调整 |

## 8. 关键难点与对策（融合后更新）

1. **集团 Embedding/Rerank 接口配额**——hash 三态保证只嵌变更块 + 失败断点续跑；仍是首要瓶颈。
2. **中文制度文档分块质量**——模板分块 + 可视化调整工具兜底；先在 50-100 篇真实文档上人工验切再定参数。
3. **冲突/质量自动裁决误判**——P2/P3 阶段审批全开，P4 起按域逐步放开；裁决留痕可回溯。
4. **反馈稀疏**——以隐式信号为主，显式为辅；REMi 抽样评估不依赖用户反馈也能发现质量回归（这是融合 REMi 后最大的缓解）。
5. **Oracle 只读**——审计/元数据/反馈日志落本地 SQLite，预留迁移路径。
6. **文档密级**——chunk 带部门标签，检索按 identity 过滤；纳入发布前安全收紧阶段。
