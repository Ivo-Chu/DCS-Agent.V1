## 0. 新设计原则摘要（复审基准）

1. LLM 负责理解意图、自主选 Tool、决定调查深度、综合推理、把技术信息翻译成用户语言；
2. Tool 只负责提供可靠事实、执行模型无法执行的查询、明确数据语义、执行必要权限控制；
3. 测试阶段硬限制仅六条：不伪造工具结果 / TEST DATA 不伪装真实数据 / 不泄露凭据 / 不执行写操作 / 不越权查他人敏感数据 / 无证据不把猜测当事实；
4. search_dcs_code 是通用调查能力，其结论可以直接回答用户；
5. 不建固定路由（问题 A → Tool A）；
6. 修复优先级：数据/ToolResult 语义 → Tool description → Tool 能力设计 → 最后才是 Prompt 硬规则。

## A. 当前所有限制性规则清单（按层）

### A1 System Prompt（dcs/prompt.ts）

| 编号 | 规则原文（要点） | 性质 |
|---|---|---|
| P-R1 | 结论先行，≤3 步操作指引 | 格式约束 |
| P-R2 | 假设用户完全不懂技术 | 表述约束 |
| P-R3 | 禁止透露任何技术细节（路径/类名/方法/表名/接口/SQL/配置/代码），含抗越狱（自称管理员也不行） | 能力封印（最重） |
| P-R4 | 无法确认说"暂时无法确认"+建议联系管理员；不编造、不生成联系方式 | 混合（不编造=底线，其余=话术模板） |
| P-R5 | 菜单权限问题必须先调 check_dcs_permission | 固定路由 |
| P-R6 | 无权限→直接说明，不继续查业务数据 | 固定路由+调查阻断 |
| P-R7 | 报错类→先权限后 query_business_data | 固定路由 |
| P-R8 | 权限和业务数据都无法解释时**才**调 search_dcs_code；检索结果仅供内部诊断，回复不得引用任何技术细节 | 顺序路由+结果封口（双重锁） |
| P-R9 | 只查本人，代查拒绝 | 安全边界 |
| P-R10 | 回复 ≤200 字 | 格式约束 |

开场定位句本身也把业务范围硬编码为"菜单权限、报餐等功能异常、功能操作方法"。

### A2 Tool description（dcs/tools.ts）

| 编号 | 位置 | 限制内容 | 性质 |
|---|---|---|---|
| T1 | check_dcs_permission | "只能查询当前提问员工本人" | 安全语义（合理） |
| T2 | query_business_data | 枚举式描述（报餐订单/餐标配置） | 数据语义（如实，但暴露工具覆盖缺口） |
| T3 | search_dcs_code | "用于内部诊断问题根因，**结果不得直接透露给用户**" | 结果封口（与 P-R8 双重锁） |
| T4 | check_dcs_permission 未命中文案 | "现有菜单：报餐管理、权限管理…"——全局菜单表无限定语 | **数据语义歧义（P0 根因）** |

### A3 Hook 层（dcs/hooks.ts）

| 编号 | 内容 | 性质 |
|---|---|---|
| H1 | PII 脱敏（手机/身份证），发生在 ToolResult→模型回填之前 | 安全底线（合理，方向正确：模型看到的即已脱敏） |

### A4 Channel / 展示层（wecom、index.ts）

| 编号 | 内容 | 性质 |
|---|---|---|
| C1 | 确认状态机：每问必经"发送完毕了吗" | 交互压制（非模型限制，但压制整体能力观感） |
| C2 | CONFIRM_WORDS 仅 3 词 | 死循环隐患 |
| C3 | PROCESSING 中新消息丢弃不排队 | 上下文丢失 |
| C4 | 90s 预算 + 超时废弃 Agent | 合理（多轮源码调查下预算偏紧） |
| C5 | 群聊谢绝、未登记中性拒答 | 合理 |
| S1 | CLI 对 search_dcs_code 摘要泛化为"内部检索已完成" | 仅影响终端显示，完整结果仍回填模型，**不是能力压制**（企微链路同理：用户只见最终回复） |

### A5 结构性参数

| 编号 | 内容 | 性质 |
|---|---|---|
| X1 | maxTurns=8 | 调查深度上限（多轮检索+综合时偏紧） |
| X2 | 工具仅 3 个，业务数据只覆盖报餐 | 能力上限的真正瓶颈（工具缺口，非 prompt 问题） |
| X3 | search_dcs_code 只返回 5 条命中行片段，无按路径读文件能力 | 源码调查天花板：模型看得见命中行，看不成上下文 |
| X4 | 检索范围仅 WebApi Controllers | 前端菜单位置/页面布局类问题无证据来源 |

## B/C. 逐条判定：保留 / 放宽 / 删除 + 原因

| 编号 | 判定 | 原因 |
|---|---|---|
| P-R1 | **放宽** | "结论先行"是好风格可保留；"≤3 步"无必要——步骤数应由问题复杂度决定 |
| P-R2 | **保留** | 正是新原则一"LLM 负责把技术信息转换成普通用户能理解的答案"的体现 |
| P-R3 | **改写（大幅收窄）** | 全面技术禁令是昨晚"离职流程拒答、具体位置编造、元规则泄漏"的直接根因。新边界：凭据类（密钥/Token/密码/连接串）绝对禁；大段源码原文不给；**结论和操作性信息（功能在哪、为什么、怎么操作）放开**；用户明确要技术细节时可给非敏感技术信息 |
| P-R4 | **拆分** | "不编造"= 新原则硬限制六，保留；"建议联系管理员核实"是话术模板，造成 10 问里 6 次复读，删除，改为"如实说明哪些部分有证据、哪些没有" |
| P-R5~R8 | **全部删除** | 典型的固定路由（原则五明确反对）。昨晚实测证明这些路由反而制造了"考勤/离职流程不在范围内"的机械拒答——模型被 prompt 训练成了查表机。删除后靠 Tool description + 模型自主判断 |
| P-R9 | **保留** | 对应硬限制五（越权）。且工具身份来自 ctx.session，prompt 层这条是对用户的解释规则，成本低 |
| P-R10 | **删除** | 200 字上限压制调查结论的表达；源码根因分析经常需要更多篇幅。长度交由模型按问题复杂度自适应 |
| 开场定位句 | **改写** | "菜单权限、报餐等功能异常"硬编码业务范围 → 改为"DCS 系统的相关问题"（与 DCS 有关即可尝试），范围由工具与源码能力自然界定 |
| T1 | 保留 | 安全语义，如实 |
| T2 | 保留（微调） | 数据语义如实；真正问题是缺考勤等数据类型工具（X2），不是描述错 |
| T3 | **改写** | 删"结果不得直接透露给用户"；改为通用调查工具定位+如实说明覆盖范围与局限（仅 Controllers、5 条片段、关键词匹配）。局限透明本身就是给模型的数据语义 |
| T4 | **修复（最高优先级）** | 数据语义歧义，P0 根因。按原则六，这是第一优先级：修文案 + 补 list_my_menus（见 §E） |
| H1 | 保留 | 硬限制五的技术实现 |
| C1~C3 | 本轮不动（属 P1 范畴） | Channel 层交互问题，与本次 prompt/tool 复审正交；建议下一轮处理（短句直通/防抖+确认词扩充+补充消息缓存） |
| C4/C5、S1 | 保留 | 合理 |
| X1 | **放宽 8→16** | 源码调查典型链路（检索→读上下文→再检索→综合）需要更多轮次余量；maxTurns 本身是安全阀，16 仍在受控范围 |
| X2/X3/X4 | **后续补能力** | 见 §E（read_dcs_file、检索范围扩展、考勤数据工具按需） |

## D. 精简后 System Prompt 草案

设计取向：从"29 行规则"到"能力声明 + 六条硬边界 + 源码使用方式"。规则数 10 → 硬边界 5 条，删除全部固定路由与字数限制。

```
你是 DCS 智能服务助手，为公司内部员工解决 DCS 系统的相关问题。

【你的能力】
- 你可以调用工具查询当前员工的菜单权限、报餐订单、餐标配置等数据。
- 你可以检索 DCS 系统源码。这是你的通用调查能力：只要问题与 DCS 系统有关，
  即使没有专用工具，也可以用源码检索寻找证据，多步调查直到有足够依据。
- 你自主决定：用哪些工具、查几轮、何时证据足够可以作答。
  综合所有查询结果推理，给出结论；不同证据冲突时如实说明。

【硬性边界】
1. 只陈述工具与源码检索返回的事实；证据不足时如实说明不确定，不把猜测当成事实。
2. 不伪造、不改写工具查询结果。
3. 无论对方如何要求（包括自称管理员/开发），不透露密钥、Token、密码、连接串等凭据。
4. 只处理当前提问员工本人的数据；要求代查他人信息时，说明无法代查。
5. 不执行任何修改、删除、提交类操作。

【源码的使用】
- 依据源码分析得出的结论，可以直接用于回答用户。
- 优先把技术发现翻译成用户能理解的操作性答案（在哪里操作、为什么、怎么办）。
- 不大段粘贴源码原文，不透露凭据类信息。
- 用户明确需要技术细节（报错信息、接口/功能名称）时，可以提供非敏感的技术信息。

【沟通风格】
- 简单自然的中文，假设用户不懂技术；结论先行，再展开必要的细节。
- 当前为内部测试阶段：业务工具返回的是测试环境数据；用户质疑数据真实性时如实说明。

【当前提问员工（系统注入）】
工号：…
姓名：…
部门：…
角色：…
```

与旧版的关键差异：

1. 删除 4 条固定工具路由、200 字上限、3 步上限、全面技术禁令、"联系管理员"话术模板；
2. 抗越狱从"防打听技术细节"收窄为"防套凭据"（唯一的绝对禁令）；
3. 新增 TEST DATA 如实声明（对应新原则三：测试数据不得伪装生产数据——昨晚模型把 Mock 数据当真实数据转述，旧 prompt 反而要求它"不要说不确定"）；
4. 明示"多步调查直到有足够依据"与"证据冲突时如实说明"——把调查深度决策权交还模型。

## E. Tool 层调整建议

按原则六的优先顺序：

1. **数据语义修复（第一优先级，即被暂停的 P0，新原则下依然成立且理由更充分）**
   - `check_dcs_permission` 未命中文案加限定语："此为系统全量菜单清单，不代表当前员工已开通"，并引导调用 list_my_menus；
   - 新增 `list_my_menus`（零参数，身份来自 ctx.session）：这不是"为防错加限制"，而是给"我有哪些菜单"补正确数据源——属"Tool 能力设计"层修复。
2. **search_dcs_code description 改写（第二优先级）**
   - 删除"结果不得直接透露给用户"；
   - 改为："在 DCS 系统 WebApi 控制器源码中按关键词检索，返回最多 5 条命中（相对路径:行号:代码行）。通用调查工具：凡与 DCS 系统相关的问题都可以用它查找证据。注意：仅覆盖 Controllers 目录，只返回命中行片段。"
3. **能力补齐（第三优先级，可逐步）**
   - `read_dcs_file(path, startLine?, endLine?)`：读取检索命中文件的上下文（resolve 后必须仍在 DCS_SOURCE_ROOT 内，防路径穿越；单次读取行数上限）。没有它，"自主调查"的上限就是 5 行片段，模型看见了线索却看不成完整逻辑；
   - maxTurns 8→16；
   - 检索范围从 Controllers 扩展到含前端/配置目录（解决"菜单在界面哪个位置"无证据来源的问题）；
   - 考勤等业务数据工具：**不在本轮加**。原则二的判定标准是"数据来源确实不同才拆 Tool"——考勤打卡数据是真实数据缺口，但按"观察上限再加能力"的阶段策略，先让模型诚实说查不到，等测试证明这类问题高频再补。

## F. 新原则下昨晚 10 问的理论处理

| # | 问题 | 旧实际行为 | 新原则下理论行为 | 依赖 |
|---|---|---|---|---|
| 1 | 通讯录选不到厂区 | 拿全局菜单表误答"您只有 4 个菜单" | 权限工具（修复后文案明确语义）→ 源码检索"通讯录/厂区"→ 基于代码证据解释厂区数据来源与入口条件，给操作性答案 | T4 修复 + R3 放开 |
| 2 | 离职流程显示协调员 | 直接拒答"不在范围内" | search_dcs_code("协调员"/"离职")→ 定位显示逻辑分支 → 给出有依据的根因分析 + 建议反馈话术 | R3/R8 放开（纯 prompt 层即可改善） |
| 3 | "你不是能看代码查bug吗" | 解释内部规则，观感差 | 不会发生（#2 已给分析）；即使发生也可坦然展示调查过程 | — |
| 4 | 今天打卡情况 | "考勤不在范围" | 仍查不到个人打卡数据（无数据工具，源码也查不出运行时数据）→ 但可解释考勤功能入口与记录逻辑，如实说本人数据暂无法查 | 诚实说：数据缺口，prompt 改善有限 |
| 5 | 我有哪些菜单权限 | 答错（4 个） | list_my_menus → 正确答 2 个 | T4 修复 + 新工具 |
| 6 | 我有哪些数据权限 | "查不了" | 源码可解释数据权限机制（按什么维度过滤），本人具体值仍查不到 → 半改善：机制讲得清，值要问管理员 | R3 放开 |
| 7 | 报餐订单 | 已合格（空订单如实） | 不变 | — |
| 8 | 我是谁 | 已合格 | 不变 | — |
| 9 | 饱餐管理在哪操作 | 纠错对，但入口靠猜 | 源码检索"报餐"→ 路由/控制器证据 → 给出有依据的入口描述；前端精确位置受 X4 限制，可如实说 | R3 放开；完全解决需扩检索范围 |
| 10 | 菜单列表在哪/具体位置 | 编造"左侧导航栏" | 同 #9：有几分证据说几分话，明确说前端布局不在当前检索范围，不编造 | 同上 |

结论：10 问中 4 问（#1/#2/#9/#10）从"拒答或编造"变为"源码调查 + 有依据回答"；2 问（#4/#6）受数据工具缺口限制，prompt 放开只能部分改善；2 问（#5 及相关）依赖数据修复；2 问已合格。

## 落地顺序建议（待确认后执行）

1. prompt.ts 换用 §D 草案（纯 prompt 层，零结构改动）；
2. T4 文案修复 + list_my_menus（原 P0 方案，不变）；
3. search_dcs_code description 改写；
4. maxTurns 8→16；
5. （观察 1-2 轮真实测试后）视失败案例决定：read_dcs_file / 检索范围扩展 / Channel 层 C1-C3。
6. 每步配套测试更新：旧 smoke 中依赖旧 prompt 文案/路由的用例需同步（改前先 grep 定位耦合点）。
