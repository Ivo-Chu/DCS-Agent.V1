## 2. 当前需要修改的发现

### R1 [P1] 新的真实三问验收仍可能把失败判为 PASS

位置：test/acceptance-live.ts:94、:106–:112、:128–:138。

问题：只依据工具启动事件和回复关键词，未要求每问正常结束、未检查 agent_error、工具结果 isError，也没有核对第二问确实查的是报餐管理和报餐订单。场景 2 的“三个关键词命中”不要求超出 7 元，场景 3 只要字符串含 35 即通过。ToolExecutionStart 仅表示尝试调用，不表示成功。

本次使用本地故障注入运行原 acceptance-live.ts：

1. 第一问查询权限管理后返回模型 API 错误，错误文字包含“系统管理员、联系、开通”。
2. 第二问错误地再次查权限管理（结果为无权限），仍继续查一个无效 dataType；最终 API 错误文字含“驳回、超出、42、35”。
3. 第三问直接 API 错误，错误文字含“35”。

**结果：退出码 0，输出“PASS：三个验收场景全部通过（真实 DeepSeek）”。**

这是对测试判定的反例，不是声称真实 DeepSeek 已出现这些响应。反例证明：测试不能排除它本来应该识别的失败。

建议最小修复：

- 每问检查本轮无 agent_error，最后 AssistantMessage 正常结束；必要工具结果存在且成功。
- 第二问检查 menuName 对应报餐管理、dataType 对应报餐订单，并确认权限成功后再查订单。
- 业务答案核对餐标 35、金额 42、超出 7 和驳回含义，允许等价表述；拒绝靠错误字符串命中关键词而通过。
- 第三问若调工具，验证 dataType 为餐标配置；除消息数增长外，检查历史与新增消息边界。
- 增加“错误回复含关键词也必须 FAIL”的测试。不要扩大到复杂评分系统。

### R2 [P2] 真实三问脚本没有打印实际回复，无法提供承诺的日志证据

位置：test/acceptance-live.ts:70–:76。

run() 打印“助手>”，await agent.prompt 得到 reply 后只打印换行。订阅器仅收集事件，并未打印 message_delta；check() 在成功时也不打印 detail。因此正常通过时，三段真实回答都不会出现在日志中。但最后又宣称“回复全文见上方日志”。

本次用正常本地响应跑该脚本，确认输出 PASS，而预置的三段回复全文没有输出。

建议：直接打印返回的 reply，保留每问工具调用与成功/失败结果；让正常通过与失败时都有可查的真实回答。采用最终完整文本即可，不需要为了验收实现复杂流式日志。

### R3 [P2] length 修复生成的提示没有显示到 CLI，用户仍看到空回答

位置：src/core/agent-loop.ts:153–:171；src/index.ts:42–:45、:94。

Loop 为截断工具调用补了说明，只通过 assistant_message 返回；CLI 只显示 message_delta，对 assistant_message 仅处理工具轮换行，而且忽略 prompt() 返回值。若模型只产生工具片段而没有文本增量，用户会看到：

```text
你> 助手>

你>
```

本次已对真实 index.ts 入口复现。原历史污染问题确实修好了，但提示尚未接到界面。若有部分文本，用户也只看到那部分，补充的截断说明仍丢失。

建议：让 CLI 能显示 Runtime 后补的文本，同时避免把已流式打印的内容再打印一遍。增加入口级验证，而不只是检查 finalText 字符串。

### R4 [P2] 员工展示仍明文打印工具参数，内部路径可从这里露出

位置：src/index.ts:46–:47。

新逻辑仅隐藏 search_dcs_code 的成功结果摘要，tool_execution_start 仍 JSON.stringify(e.args) 原样显示。模型可能根据上一轮源码结果，继续用文件路径、类名或方法名作搜索关键词，这些内容将从参数日志露出。

本次本地模型返回搜索关键词 `Luxshare.DCS.WebApi/Controllers/ReviewProbe.cs`（合成的测试路径），实际 CLI 同时显示了这个路径和“内部检索已完成”。所以成功摘要隐藏已生效，但不能声称整个用户输出都没有源码路径。

建议：员工界面只显示“正在内部检索”等状态，不打印原始工具参数；检查失败摘要/错误提示是否也带内部内容。日志如需完整细节，应明确作为开发调试输出。无需在 core 里硬编码 DCS 脱敏规则。

局限：这不证明真实模型自然输出一定泄露源码；它证明确定性的 CLI 展示通道没有覆盖完整。Prompt 遵守情况仍待真实模型验证。

### R5 [P2] 检测到坏 SSE 帧后还会等待下一块数据，可能一直不结束

位置：src/core/model/deepseek.ts:163–:164、:188–:189。

坏 JSON 分支设置 badFrame=true 后，只 break 内层逐行循环。随后 for-await 先等待下一次流读取，读到后才进入循环体执行 if(badFrame) break。如果对端此时保持连接、不再发送数据，程序无法到达后面的错误事件。

本次构造“立即发坏 JSON、随后保持连接打开”的 ReadableStream：100ms 后仍未返回错误；主动关闭流后才收到 error。这里的 100ms 是确认控制流被卡在额外读取上，不是建议设置 100ms 网络超时。

建议：在发现坏帧时直接结束外层读取并产出错误（例如带标签 break 外层循环），不再请求下一块数据。补“坏帧后不 EOF”的回归测试。已有 H1/H5 都用自动结束的字符串 Response，未覆盖此路径。本项不要求增加全局超时或复杂停止策略。
